# Operator runbook

1. Open `/admin`, enter `ADMIN_TOKEN`, and inspect paid orders and full delivery addresses including country. Customers can complete real payment even when the U1 or gateway is offline; the storefront explains the delay. Avoid sharing screenshots of the admin view.
2. Check the printer is idle, the matching 1–4 copy pre-sliced plate files exist, filament and bed are ready, and the gateway is armed. Press **Create batch** for the first plate. Postgres admits only one unconfirmed plate at a time; new orders can arrive and be paid while this plate prints.
3. The gateway polls the API, atomically claims the current batch, records a persistent journal entry, checks printer idle state, uploads the chosen G-code and starts it once. The dashboard moves BATCHED → PRINTING → PRINTED. The actual U1 reports completion through Moonraker. Inspect the physical plate, then click **Confirm plate & queue next four**. The server atomically selects an older queued plate or up to four paid orders; the gateway starts that new batch on its next poll. If there are no waiting orders, create the next batch manually once orders arrive.
4. In **Ready to ship**, pack each token, use the private order address and country, then **Mark sent** individually. Use **Load more shipping addresses** for older outstanding prints. No shipping label is created automatically.
5. If a job shows NEEDS_REVIEW or gets stuck in DISPATCHING/PRINTING, inspect Moonraker, gateway logs and `/data/{batch-id}.json` before any restart. The journal deliberately stops automatic duplicate launches. A stuck batch must be resolved manually before its orders can be requeued; do not restart or remove the journal while the printer may still be running.
6. For a completed plate with a failed object, click **Needs reprint** on that PRINTED order. For an order already NEEDS_REVIEW, inspect the physical plate and previous job, then click **Return to print queue** and confirm. This moves that paid order to PAID and records the previous batch in `order_events`. It does not start a print. Click **Create batch** to combine it with other paid orders into a new plate, and supervise the printer. Never use the old batch ID to retry an uncertain start. If you refund, send ADA manually, verify the transfer, then mark **REFUNDED**. That label alone does not send money.
7. If the U1 is offline before a queued job is claimed, the job stays QUEUED and resumes when the gateway sees an idle printer and the four plate files. If the gateway claimed a job and then lost contact, inspect the physical U1 and journal. In `/admin`, select **Review stopped / uncertain job** only after confirming the old job stopped, return affected orders to the print queue, and confirm the reviewed plate. Then select **Arm / resume gateway** after confirming the U1 is idle. The gateway observes this command on its outbound poll. A successfully completed print rearms automatically; admin confirmation still gates the next launch. Back up Neon and the persistent journal. Use **Pause new orders** when you cannot commit to delayed fulfillment.

## Order states

`AWAITING_PAYMENT → PAID → BATCHED → PRINTING → PRINTED → SHIPPED`; exceptions are `NEEDS_REVIEW` and manually recorded `REFUNDED`. A physically reviewed `NEEDS_REVIEW` order can return to `PAID` for a new batch; it is never charged again. Batches use `QUEUED → DISPATCHING → PRINTING → PRINTED`. Orders and batches remain private. A transaction hash, when available, links to Cardanoscan.

## Payment ambiguity

The browser preserves a signed payload in session storage and presents **Recheck signed payment** after an interrupted request. It resends the same signature. Do not ask a customer to sign another transaction while status is uncertain. The operator must reconcile the transaction in the explorer and database if facilitator settlement succeeds but persistence fails. No automatic refund or on-chain reconciliation daemon exists in this version.

## Recovering orders during an incident

- **Printer offline:** keep sales open if you can honor the delivery delay. Payments do not depend on Moonraker. Restore the printer and gateway, inspect the empty plate, then use **Arm / resume gateway**. A first batch needs **Create batch**; subsequent batches wait for **Confirm plate & queue next four**. A partial queue creates a plate of 1–3 rather than waiting indefinitely for four.
- **Ambiguous payment:** search for the customer's email or full order ID. Use **Reconcile stored payment**. This uses the original signed transaction and the official SDK; it never creates a second payment. A saved successful receipt can complete the order even while the facilitator is unavailable. An in-progress attempt returns 409. After a hard process crash its lease expires after 15 minutes. A failure before the receipt was saved still requires the facilitator to reconcile the original transaction; if it cannot, inspect its logs and the chain. Do not ask the buyer to sign again just because the HTTP request timed out.
- **Gateway stopped mid-print:** stop any old gateway instance and physically inspect the U1. Use **Review stopped / uncertain job**. For each object choose **Inspected: print OK**, return it to the print queue, or record a refund already performed. Confirm the old plate, then arm the gateway. Never delete journal files to force an old batch to print again.
- **Damaged or lost shipment:** find the order, choose **Needs reprint**, then **Return to print queue** after inspection. This retains the payment and records the old batch in `order_events`. A new batch ID is mandatory.
- **Shipping:** use Ready to ship for full name, email, address and country; mark sent only after dispatch. Historical orders are searchable and paginated. Dashboard counters cover all orders, not only the displayed page. Delivery is still limited to Germany; adding destinations also requires shipping price and delivery-policy decisions.
- **Traffic spike:** Node admits at most 100 active requests and the local database pool queues at most 100 waiting queries. Excess requests fail with a retryable 503; signed payment retries reuse the same transaction. These are per-process limits, not an Internet abuse defense. Configure edge rate limits for order creation and failed admin authentication; permit larger bursts for payment retries and keep the private gateway paths reachable. Scale API instances against a appropriately sized shared Postgres/Neon pool; keep exactly one gateway per physical printer.

## Backups, monitoring and rollout

1. Back up before applying migrations. Migration `007_payment_recovery.sql` only adds columns and an index. Never run `docker compose down -v` on an installation with orders.
2. Maintain encrypted daily Postgres backups plus point-in-time recovery where available. For local Compose, `docker compose exec -T db pg_dump -U print -d print -Fc > orders.dump` produces a backup. Restore into a separate database and verify order totals, payment attempts and current plate before trusting the backup. Restrict access: the dump contains customer addresses and signed payment payloads.
3. Preserve the `gateway_data` volume along with the database. After restoring either from backup, keep the gateway disarmed and reconcile the physical printer and latest chain payments before resuming. A database backup may predate a payment or a physical print.
4. Monitor `/api/health` for configuration and `/api/ready` for database reachability. Alert on repeated 5xx, stale gateway heartbeats, long-lived AWAITING_PAYMENT attempts, NEEDS_REVIEW jobs, queue age and disk capacity. Printer downtime alone must not fail API readiness.
5. Rebuild with `docker compose up -d --build`. Compose uses static Nginx assets and non-watching API/gateway processes with restart policies. Configure `FRONTEND_ORIGIN` for the public HTTPS origin. Blockfrost browser project IDs are frontend build arguments: rebuild after changing them. The reverse proxy must allow a 64 KB payment signature header and a 300-second upstream timeout. Node and bundled Nginx have matching limits.
6. Before accepting public sales, complete a real preprod wallet payment with the printer offline, reconcile after interrupting a response, restart the gateway mid-job, inspect a failed plate, reprint, and ship. Load-test your actual facilitator/database deployment. Automated tests mock the facilitator and cannot certify on-chain or mechanical outcomes.

The gateway starts disarmed by default in Compose. Arming from the dashboard requires an idle reachable printer; a pending arm request remains pending while it is offline. Refund buttons record bookkeeping only and do not transfer funds. Protect `/admin` with HTTPS and preferably an access proxy, use independent random tokens of at least 32 characters, and lock the dashboard when finished.
